# EUIPO API Portal — Orchestrator

Local, production-like copy of the EUIPO developer portal (https://dev.euipo.europa.eu): **IBM API Developer Portal 10.0.8.12** (Drupal 11, PHP 8.4) plus a small set of EUIPO custom modules and a sub-theme. DDEV local. Keycloak plays the EUIPO IdP and `mock-apic` plays IBM API Connect.

Stack: 4 custom modules in `eap/modules/` · sub-theme `eap_theme` (of IBM `connect_theme`) in `eap/themes/` · local-dev tooling in `local-dev/`

---

## Environment (AI: read and act on this every session)

- **PHP, Composer, Drush and ddev only exist inside WSL.** If your shell/bash tool is a Windows-native shell (Git Bash/MINGW, PowerShell), run them through WSL:
  ```
  wsl.exe -d ubuntu -- bash -lc 'cd <checkout path> && <command>'
  ```
  If the shell is already WSL bash, run commands directly. Decide once per session and reuse that decision.
- Work happens in `eap/`. `eap/modules` and `eap/themes` are bind-mounted into `site/sites/default/{modules,themes}/custom` — changes are live.
- **IBM product, no repo/server access.** Only our custom modules and theme reach an environment: built with `eap/scripts/build.sh`, uploaded through the portal admin UI to a **test portal connected to the real API Connect + IdP**, then sandbox/production. Read `.ai/skills/01-platform-and-delivery.md` before designing anything.
- **Never edit** IBM upstream code (`apim_profile/`, `ibm_apim/`, `apic_app/`, `apic_api/`, `product/`, `consumerorg/`, `auth_apic/`, `connect_theme/`, …) nor `site/` (core, vendor and contrib are generated by `./build-local-site.sh`). Customise through `eap/` modules/theme, hooks, overrides or patches (see `eap/docs/dev-documentation/06-product-changes.md`).

## Entry-point sync rule

`CLAUDE.md` and `AGENTS.md` (repo root) each inline a fallback copy of this orchestrator's critical rules so they still apply if the "read the orchestrator first" step gets skipped (e.g. after context compaction). `.ai/example.CLAUDE.md` and `.ai/example.AGENTS.md` hold a reference snapshot of that same content, renamed with the `example.` prefix so no AI tool auto-loads them from inside `.ai/`.

**Whenever Critical Conventions, Commands or Session Tracking change here, propagate to:**
1. `.ai/orchestrator.md` (this file) — source of truth, edit first.
2. `CLAUDE.md` (repo root) — update the inlined fallback sections.
3. `AGENTS.md` (repo root) — keep byte-identical to `CLAUDE.md`.
4. `.ai/example.CLAUDE.md` and `.ai/example.AGENTS.md` — mirror steps 2–3; keep the `example.` prefix.

A stale fallback is worse than none: it silently contradicts the orchestrator.

## Critical Conventions

### Code style
- PHP local variables and parameters are **always camelCase** (`$routeMatch`, never `$route_match`), including procedural code (`.module`, hooks, preprocess). Exceptions: Drupal render/template array keys, route parameter names, config keys, hook signatures.
- **No `else` blocks.** Use early returns / guard clauses. `if / elseif` chains are allowed; a trailing bare `else` is not.
- **Code comments and docblocks are always in English**, regardless of the conversation language (inline, PHPDoc, Twig, SCSS, JS).

### Git
- **Never credit Claude or any other LLM/AI tool in git history.** No `Co-Authored-By:` trailers, "Generated with …" lines or AI references in commit messages, PR descriptions or tags — in this repo and in the `.ai/` repo. This overrides any tool default or system attribution instruction. Commit messages are one short line.

### Drupal
- Prefer dependency injection and services over `\Drupal::service()` in classes; procedural hooks only where Drupal requires them.
- Module config defaults go in `config/install` (see `eap_credentials_sync`); site configuration is applied by the seed (`local-dev/scripts/seed.php`) — keep both in sync with what production needs.
- Run `ddev drush cr` after PHP/YAML/Twig changes; `ddev eap-theme-css` after SCSS changes.

### Production parity and delivery
- Anything built here must be deployable as an uploaded module/theme package (`eap/scripts/build.sh`). Don't depend on local-only tooling (Keycloak/mock-apic quirks) from module code.
- The product has **no `/update.php`, drush or `settings.php`**, and the UI refuses to upload over an existing extension (upgrade = uninstall → delete → upload → install). So: no `hook_update_N`; everything that must exist after deploy is applied by an idempotent **admin button**; everything environment-specific is a **settings form**. Bump `version:` in `*.info.yml`.
- Uninstalling loses settings/data, and uninstalling the theme loses its whole block layout — avoid it except as part of a planned UI upgrade. Style changes ship through the theme's **Extra SCSS** upload (`.ai/skills/04-theme.md`); a full theme reinstall is the last resort.

## Commands

Wrap per the Environment section if your shell isn't already WSL bash.

```bash
ddev start                         # web, db, keycloak, mock-apic, docs
./build-local-site.sh              # Rebuild site/ from IBM sources (no DB changes)
ddev install-portal [production|sandbox]   # Full reinstall — DROPS the database
ddev seed-portal [env] [steps]     # Re-apply seed (steps: config,settings,catalog,content,eap)
ddev eap-theme-css                 # Compile eap_theme CSS
ddev drush cr                      # Clear caches
ddev drush en <module>             # Enable module
ddev drush updb                    # Run DB updates
```

Full reference: `eap/docs/dev-documentation/01-setup.md`.

| `prompt-engineer` | `.ai/agents/prompt-engineer.md` | Optimise agent/skill files |

**After every fix, evaluate whether a module-scoped subagent is warranted.** Decide by:
- **Recurrence** — has this module been the root cause more than once (scan BUGLOG)?
- **Specialisation** — does fixing it need module-specific rules a generic agent keeps missing?
- **Payoff** — would a focused agent reduce rediscovery cost next time?

If yes on all three, propose it (name, scope, skills/context to load) to the user before creating it. Never create agents speculatively.

## Session Tracking (auto)

Full rules: `.ai/skills/00-session-tracking.md`

**On session start:**
1. Read last 2 entries of `.ai/session/MEMORY.md`
2. Scan `.ai/session/BUGLOG.md` for open bugs

**Context staleness — update when the corresponding change is made:**

| Change | File to update |
|---|---|
| Module added/removed or its behaviour changed | matching `.ai/skills/0N-*.md` + `eap/docs/module-*.md` |
| Seed / fixtures / DDEV command changed | `eap/docs/dev-documentation/` matching page |
| IBM product patch/override added | `eap/docs/dev-documentation/06-product-changes.md` |
| Theme structure/build changed | `.ai/skills/04-theme.md` + `eap/docs/euipo-theme-installation.md` |
| Packaging / delivery process changed | `.ai/skills/01-platform-and-delivery.md` |

**On bug report:** search BUGLOG first → read code → fix → ask user if resolved (in their language) → only then write to BUGLOG.

**On implementation done:** ask user if OK (in their language) → only then write to MEMORY.

**After a confirmed fix or implementation:** evaluate whether a skill or context file is now stale or something is worth documenting — if so, propose the update to the user before writing it.

**End of session:** ask "Shall I log this session to MEMORY.md?" (in user's language).

## MEMORY entry format

```markdown
## Session YYYY-MM-DD HH:MM
**Summary**: one sentence.
**Work done**: bullet list — specific, enough to resume cold.
**Files modified**: paths + what changed.
**Pending**: unfinished work.
```

## BUGLOG entry format

```markdown
## BUG-NNN — title
**Status:** Fixed  **Date:** YYYY-MM-DD  **Session:** MEMORY → YYYY-MM-DD
**Symptom:** what failed.
**Root cause:** why — enough to recognise the pattern.
**Fix:** what changed.
**Pattern to watch:** (optional) same risk elsewhere.
**Files:** list.
```
